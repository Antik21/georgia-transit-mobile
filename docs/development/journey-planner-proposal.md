# Построение маршрута A→B: ресерч и план реализации

Статус: решения приняты в ADR 0022 и ADR 0023, веб-MVP реализован. Дата: 2026-11-12.

> Изменение после MVP: режимов-фильтров («быстрее», «меньше пешком», «без пересадок») больше нет.
> BFF возвращает все допустимые варианты (до 6) с метками «Оптимальный», «Быстрее всего»,
> «Меньше пешком», «Без пересадок», как на сайтах авиабилетов, а у каждой метки постоянный цвет.
> Актуальные правила — в разделе Selection [ADR 0022](../adr/0022-batumi-in-house-journey-planner.md);
> упоминания режимов и «1–3 вариантов» ниже относятся к исходному предложению.

## 1. Цель

Пользователь выбирает точку на карте и нажимает «Построить маршрут». Приложение показывает 1–3
лучших варианта на общественном транспорте. В каждом варианте видно:

- сколько идти до остановки посадки;
- сколько идти между остановками при пересадке, если остановки разные;
- сколько идти от последней остановки до точки назначения;
- сколько ждать автобус, сколько ехать и общее время.

Следующий этап: оптимизация по живому прибытию автобусов. Например, более дальняя остановка, куда
автобус придёт через 5 минут, лучше ближней, где его ждать 30 минут.

## 2. Как это сделано в batbus.app/map

Разбирали публичный бандл `mapChunk-*.js` и сетевые запросы 2026-11-12.

### 2.1 Архитектура

Планировщик работает **целиком в браузере**. Отдельного серверного эндпоинта для плана нет.

| что | откуда |
| --- | --- |
| Каталог сети: остановки с `routes{Order, Status}` и геометрия маршрутов | `GET /api/getDbData` (формат Theta, тот же, что читает наш `BatumiThetaTransitProviderAdapter`) |
| GPS автобусов | `GET .../getAllBuses`, опрос примерно каждые 5 с (тот же фид, что в ADR 0011) |
| Расписания маршруток | `GET .../schedules` |
| Пешие отрезки | `GET .../walk?from=lat,lon&to=lat,lon` возвращает `{coords:[[lat,lon]…], dist}`. Это свой пешеходный роутер на OSM. Его вызывают только для отрисовки выбранного варианта: A→остановка, остановка→B, A→B напрямую |

Вывод: у batbus **те же исходные данные, что у нашего BFF для Батуми**. Их модель ETA (длина цепочки
остановок / скорость маршрута + 1 мин на промежуточную остановку) совпадает с нашей из ADR 0012.

### 2.2 UX

- Кнопка режима «A→Б». Подсказка: «Откуда поедете? Нажмите на карту или найдите адрес». Есть кнопка
  «Моя геопозиция». Тап по карте ставит A, следующий тап ставит B.
- Результат появляется в нижней шторке. Строка варианта выглядит так:
  `442м · [2A] ул. Ильи Чавчавадзе №94 → ул. Нижарадзе · 106м`.
  Раскрытый вариант показывает шаги «идти → ждать → ехать → (пересадка) → идти». Прямой вариант
  рисуется на карте цветом маршрута, пешие куски — пунктиром.
- Фильтры: «Быстрее», «Меньше пешком», «Без пересадок» и переключатель «+5 мин на пересадку».
- Кнопки «Я еду» (режим сопровождения поездки) и «Сохранить без сети».
- Монетизация. В бесплатном «обычном» планировщике варианты сортируются по ходьбе. «Умный»
  планировщик в Premium учитывает время ожидания по живым автобусам.

### 2.3 Алгоритм

Восстановлен по функциям `Gc`, `tp`, `q5`, `Y5`.

1. Считается расстояние по прямой (Haversine) между A и B.
   - Если оно ≤ 500 м, предлагается только «пешком».
   - Если ≤ 3 км, вариант «пешком» добавляется к остальным.
2. Кандидаты на посадку и высадку: все остановки в радиусе **900 м** от A и от B.
3. **Прямые варианты.** Для пары остановок (у A, у B) ищется общий маршрут с тем же `Status`
   (направлением), причём `Order` посадки должен быть меньше `Order` высадки. На каждый маршрут
   остаётся одна пара — с минимальной суммарной ходьбой.
4. **Варианты с одной пересадкой.** Пересадок бывает максимум одна.
   - Берутся 8 ближайших к A остановок. Для каждого их маршрута перебираются остановки ниже по ходу,
     не ближе чем через 3 остановки.
   - Пересадка возможна на той же остановке или пешком на остановку в радиусе **800 м**.
   - Второй маршрут тоже проезжает минимум 3 остановки до остановки у B.
   - Для каждой пары маршрутов `r1:r2` остаётся лучший вариант по грубому времени. Всего остаётся
     топ-6.
5. **Время.**
   - Ходьба: `dist × 1.25 / 83 м/мин`, то есть около 5 км/ч с коэффициентом извилистости 1.25.
   - Поездка: ETA вдоль цепочки остановок. Если её нет, берётся `Haversine × 1.3 / скорость маршрута`.
   - Ожидание: ближайший живой ETA, который не раньше «пришёл на остановку + 1 мин» (5 мин в режиме
     «+5»). Если живых автобусов нет, ожидание принимается равным **15 мин**.
   - Вторая посадка считается так же, но относительно прибытия на пересадку.
6. **Ранжирование.**
   - Вариант с пересадкой остаётся, только если он быстрее лучшего прямого. В режиме «меньше пешком»
     он также остаётся, если экономит не меньше 150 м ходьбы.
   - Сортировка идёт по `totalMin`. В режиме «меньше пешком» сначала по ходьбе, округлённой до 50 м,
     затем по времени.
   - Варианты дольше 90 мин отбрасываются.

### 2.4 Слабые места, которые стоит сделать лучше

- Для прямых вариантов пара остановок фиксируется **по минимальной ходьбе до расчёта времени**.
  Поэтому случай «дойти на 1–2 остановки назад и сесть в автобус раньше» на том же маршруте не
  находится. Это ровно сценарий из нашей задачи.
- Пересадка максимум одна. Перебор жадный: 8 ближайших остановок и топ-6 по грубому времени.
- Без живых данных ожидание фиксировано и равно 15 мин. Реальный интервал не оценивается.
- Ходьба при ранжировании считается по прямой × 1.25. Настоящий пешеходный роутинг нужен только
  для рисования.

## 3. Что уже есть у нас

### 3.1 BFF (`:transitBff`)

- Есть контракт `GET /v1/cities/{cityId}/journeys` с полями `Journey`, `JourneySegment` (`TRANSIT`,
  `WALK` и другие) и `JourneyPage`, а также capability `tripPlanning`.
- Для координат действуют правила приватности ADR 0008: no-store, без кэша и без LKG.
- Батуми (Theta) — единственный город в проде, и у него `tripPlanning=false` (ADR 0013).
  `docs/development/batumi-theta-evaluation.md:141` прямо запрещает trip planning для Theta.
  **Чтобы его включить, нужен новый ADR.**
- В памяти BFF уже лежит всё, что нужно роутеру:
  - `BatumiCatalog` с `stopOrderByRoute` (порядок по `Status`/`Order`);
  - `RouteCycle` с накопленными метрами;
  - таблица скоростей по маршрутам;
  - shapes;
  - живой снапшот автобусов и ETA по ADR 0012 через `arrivals` и `routeArrivals`.
- **Расписаний и интервалов нет.** Интервал можно оценить только по живым машинам на линии.

### 3.2 Shared и платформы

- Domain, репозиторий и клиент для journeys есть: `TransitModels.kt`, `TransitRepository.kt`,
  `BffTransitRepository.kt`, `TransitBffClient.kt`. UI нет.
- В `MapPlatformEvent` нет тапа в произвольную точку. Есть только `StopTapped`, `VehicleTapped` и
  `ViewportSettled`.
  - Android: `onMapClick` уже получает `LatLng` и на промахе возвращает `false`. Событие добавляется
    дёшево.
  - iOS: нужен `mapView.convert(point, toCoordinateFrom:)` в `MapLibreMapViewBridge.swift`.
- `MapPolyline` требует `RouteId`. Пунктира для ходьбы нет, слоя маркеров A/B нет, на iOS opacity
  принудительно равна 1.
- `MapViewModel.kt` занимает 523 строки, то есть уже больше 500. Логику планировщика выносим
  в отдельную feature по ADR 0018, не в ViewModel.
- Отправку координат пользователя с мобильного клиента убрал ADR 0016. Вернуть её можно только
  через новый ADR.

## 4. Выбор движка

| вариант | плюсы | минусы | лицензия |
| --- | --- | --- | --- |
| **A. Свой RAPTOR-lite в BFF на данных Theta** (рекомендуется) | Данные и живые ETA уже в памяти. Сеть маленькая (десятки маршрутов, ~1k остановок), поиск укладывается в миллисекунды. Умеет ожидание по живым машинам и 2 пересадки. Нет новой инфраструктуры | Код свой, нужны тесты. Нет OSM-ходьбы, пока не подключён пешеходный роутер | своя |
| B. Self-hosted MOTIS 2 | Готовый мультимодальный роутер с OSM-ходьбой и GTFS-RT | Нужно синтезировать GTFS (`frequencies.txt`) и GTFS-RT из Theta. Отдельный сервис, OSM-препроцессинг, больше памяти на Render | MIT |
| C. OpenTripPlanner 2 | Зрелый, есть RAPTOR и OSM-ходьба | Тяжёлый (JVM, граф на гигабайты для страны). Те же проблемы с GTFS. Дорого держать | LGPL-3.0 |
| D. Hosted Transitous | — | Батуми нет в покрытии. Политика запрещает коммерческое и нагруженное использование (ADR 0006) | — |
| E. Планировщик на клиенте, как у batbus | Координаты не уходят с устройства, работает офлайн | Приложению понадобится весь граф, все машины и ETA-модель (провайдерская логика ADR 0012). Это противоречит правилу «provider-specific contracts never enter the app» | — |

**Рекомендация: A.** Роутер стоит за интерфейсом `JourneyPlanner` в BFF. Если появятся
мультигородские GTFS-фиды, можно будет перейти на B (MOTIS) без изменения публичного контракта.

### Пешие отрезки

- **Этап 1.** Haversine × 1.3 при скорости 1.3 м/с (около 78 м/мин, с запасом), с пометкой «≈».
- **Этап 2.** Self-hosted **GraphHopper** (Apache-2.0, Java), встроенный прямо в JVM BFF как
  библиотека. Отдельный сервис не нужен.
  - Граф строится из Geofabrik-выгрузки Грузии, обрезанной `osmium` до bbox Аджарии. Это десятки МБ.
  - Матрица пешего пути «остановка ↔ остановка» до 800 м предрасчитывается при обновлении каталога.
    Координат пользователя в ней нет, кэшировать её можно.
  - Отрезки «от пользователя» и «до точки» считаются on-demand и не кэшируются.
  - Данные OSM лицензированы ODbL; атрибуция «© OpenStreetMap» уже есть в приложении.
- Альтернативы: OSRM (BSD-2) или Valhalla (MIT) отдельным контейнером. Публичный демо-сервер
  OSRM/OSM в проде использовать нельзя.

## 5. Алгоритм (предлагаемый)

Это time-dependent RAPTOR с частотной моделью. Каждая «поездка» — либо конкретная живая машина,
либо виртуальный рейс с ожиданием по оценке интервала.

```text
вход: O, D, t0 = now, prefs{mode, transferBuffer}, maxTransfers = 2
1. access  = остановки в радиусе 1000 м от O, τ0(s) = t0 + walk(O, s)
   egress  = остановки в радиусе 1000 м от D
   direct  = пешком O→D, если ≤ 2 км или быстрее любого транзита
2. для k = 1..maxTransfers+1:
     для каждого паттерна p (маршрут + Status), задетого отмеченными остановками:
       идём по остановкам p по порядку (кольцо — только если RouteIsCircle);
       посадка в s: dep = первая живая машина p с ETA(s) ≥ τ(s) + buffer,
                    иначе τ(s) + headwayEstimate(p), basis = ESTIMATE;
       для s' ниже по ходу: arr = dep + ride(p, s→s')
         (ride = Δcum / скорость маршрута + 60 с × промежуточные, как в ADR 0012;
          для живой машины = ETA(s') − ETA(s) той же машины)
       если arr улучшает τk(s') по Парето (время, ходьба) → отметить s'
     пешие пересадки: из отмеченных s' на соседей ≤ 800 м по предрасчитанной матрице
3. для egress-остановок: arrive(D) = τk(s) + walk(s, D); собираем Парето-фронт
   (время прибытия, ходьба, число пересадок)
4. выбор 1–3 вариантов (см. ниже)
```

- **Оценка интервала** `headwayEstimate(p)` = длина кольца / (скорость × число активных машин на
  линии). Ожидание берётся консервативно, примерно 0.6–1.0 интервала. Если машин на линии нет,
  маршрут не предлагается или помечается «автобусов на линии нет».
- **Сценарий «дальняя остановка, но автобус раньше»** закрывается сам. Мы перебираем все остановки
  в радиусе, считаем время каждой посадки и не фиксируем ближайшую. В том числе рассматриваем посадку
  выше по ходу того же маршрута, чтобы успеть на более ранний автобус.
- **Выбор вариантов.** Из Парето-фронта берём:
  1. самый ранний по прибытию;
  2. лучший без пересадок (или с меньшим их числом);
  3. лучший по ходьбе.

  Затем убираем дубли по сигнатуре маршрутов. Отбрасываем варианты дольше `min + max(15 мин,
  50%)`. Пересадочный вариант оставляем, только если он экономит не меньше 5 мин или прямого
  варианта нет.

  Веса для внутреннего «generalized cost»: ходьба × 1.5, ожидание × 1.2, штраф за пересадку 4 мин.
  Режимы как у batbus: «быстрее», «меньше пешком», «без пересадок», «+буфер на пересадку».
- **Производительность.** Батуми: ~60 паттернов × ~1000 остановок × 3 раунда — единицы
  миллисекунд. Отдельный пул не нужен, но обязателен таймаут и ограничение конкурентности.

## 6. Контракт BFF (аддитивно, `/v1`)

Новая операция `POST /v1/cities/{cityId}/journeys/plan`. Координаты передаются в теле, а не
в query: так же, как в walking-estimate, чтобы не попасть в логи и URL.

```text
request:  { from:{lat,lon}, to:{lat,lon}, departureAt?: UTC, maxTransfers: 0..2,
            mode: FASTEST|LESS_WALKING|FEWER_TRANSFERS, transferBufferSeconds, locale }
response: JourneyPage {
  items: Journey[1..3] {
    id, departureAt, arrivalAt, transfers,
    + durationSeconds, walkingDistanceMeters, timingQuality: LIVE|MIXED|ESTIMATED,
    segments: JourneySegment[] {
      mode: WALK | TRANSIT, startsAt, endsAt, fromPosition, toPosition,
      + distanceMeters, + geometry (encoded polyline: срез shape для TRANSIT, пеший путь для WALK),
      + geometryApproximate (WALK по прямой на этапе 1),
      TRANSIT: routeId, directionId, fromStopId, toStopId,
        + intermediateStopCount, + waitSeconds, + waitBasis: LIVE_VEHICLE|HEADWAY_ESTIMATE,
        + vehicleId?
    } } ,
  observedAt, source: CLIENT_ESTIMATE, realtime, stale }
headers: Cache-Control: no-store; без координат в логах, метриках и ключах SingleFlight
```

- Ожидание сделано полем `TRANSIT`-сегмента, а не новым `mode: WAIT`. Новое значение enum сломает
  старые строгие клиенты.
- `NormalizedResponseValidator` нужно научить принимать `source=CLIENT_ESTIMATE` для journeys.
- Старый `GET /journeys` остаётся для совместимости.
- Capability: Батуми получает `tripPlanning=true` через control plane и ADR.

## 7. Мобильный клиент (shared)

1. **Точки A и B (ADR 0023).**
   - `JourneyEndpoint = CurrentLocation | MapPoint(GeoPoint)`. Любая сторона может быть точкой на
     карте, «Моя геопозиция» — максимум одна. Работает swap A↔B.
   - Добавить `MapPlatformEvent.MapLongPressed(GeoPoint)`. Long-press — стандарт Google и Apple
     Maps, он не конфликтует с закрытием шторки и панорамой.
   - Long-press ставит пин с действиями «Сюда» и «Отсюда».
   - Панель планировщика с полями A и B. Каждое поле — «Моя геопозиция» или «Точка на карте».
     Есть swap и сброс.
2. **Геопозиция.** Разрешение запрашиваем только по явному выбору «Моя геопозиция». Фикс не старше
   120 с и точностью до 250 м. Без разрешения маршрут A→B по точкам работает полностью. Координаты
   округляются до 4 знаков, в BFF не передаётся, какая из точек — геопозиция.
3. **Presentation.**
   - Новая `JourneyPlannerFeature` (handler по правилам MVI из ADR 0018) со своим срезом
     `ViewState.planner`: `Idle | PointPicked | Loading | Results(options, selectedId) | Error |
     Unavailable`.
   - Запросы работают в режиме latest-wins.
   - Пока шторка открыта, план пересчитывается каждые 30–60 с: ETA меняются. Пересчёт
     останавливается в фоне и при закрытии.
   - `MapViewModel` только делегирует.
4. **UI.**
   - Шторка со списком из 1–3 карточек. Пример: `≈ 41 мин · прибытие 15:32` и строка шагов
     `🚶 6 мин 450 м → [2A] ждать ~4 мин • 9 ост. → 🚶 2 мин 120 м → [10] … → 🚶 3 мин 210 м`.
   - Метка «live» или «по интервалу» у ожидания.
   - Чипы режимов.
   - Дисклеймер «время ориентировочное».
5. **Карта.**
   - Обобщить `MapPolyline`: `RouteId` становится опциональным, добавляется стиль
     `Route(color) | Walk(dashed)`.
   - Новый слой маркеров: A, B, посадка, высадка, пересадка.
   - Android и iOS: `lineDasharray`.
   - iOS: убрать принудительную opacity для пеших линий.
6. **Навигация.** Всё живёт внутри Map, новых routes нет. Если позже появится экран деталей,
   в route передаётся только типизированный id.

| 2 | Mobile MVP | Long-press, пин B, гео-A. `JourneyPlannerFeature`, шторка с 1–3 вариантами. Отрисовка: срез shape и пеший пунктир. Android и iOS bridges. Smoke-тесты | L |
| 3 | Пешеходный роутинг | Встроенный GraphHopper с OSM-выгрузкой Аджарии. Предрасчёт матрицы «остановка ↔ остановка». Пешая геометрия в сегментах. ADR на OSM-данные и пешеходный движок | M |

## 9. Риски

- **Данные.** Семантика `Status` у кольцевых маршрутов. Ограничение ETA в 45 мин из ADR 0012
  урезает горизонт второй посадки.
- **Нет расписаний.** Ночью и на линиях с одной машиной интервал не оценить. Честно показываем
  «нет автобусов на линии».
- **Приватность.** Координаты A и B — чувствительные данные. Действуют правила no-store, без логов,
  без кэша, плюс редактирование в debug-инспекторах (уже сделано для walking-estimate).
- **Нагрузка на Render (один инстанс).** Роутер лёгкий. GraphHopper на этапе 3 добавит память,
  поэтому граф строим только для bbox Аджарии.
- **Лицензии.** Всё бесплатно: свой код, GraphHopper (Apache-2.0), OSM (ODbL, атрибуция), MOTIS
  (MIT) и OTP (LGPL) как запасные варианты.
