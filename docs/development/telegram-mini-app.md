# Telegram Mini App

Второй этап после [подготовки общей логики](telegram-web-preparation.md). Решения зафиксированы в [ADR 0020](../adr/0020-telegram-mini-app-web-client.md). Веб-клиент в `webApp` остаётся адаптером: состояние, запросы к Transit BFF и правила навигации принадлежат `:shared` и доходят до браузера через Kotlin/JS-мосты в `shared/src/jsMain/.../bridge`. Каждый срез ниже — отдельный PR от `main` со своими проверками.

## Срез 2. Автобусы в реальном времени — ветка `feature/telegram-live-vehicles`

В `:shared` уже есть всё поведение: опрос `/v1/cities/{cityId}/vehicles`, интерполяция по линии маршрута, `MapRenderState.vehicles` (`MapVehicleMarker`), `VehicleLayerState` и `MapPlatformEvent.VehicleTapped`. Не хватает моста и веб-рендера.

- [x] Отдельная подписка `MapBridge.subscribeVehicles` с экспортированными `VehicleItem` (id, маршрут, координаты, азимут, `positionKind`, подпись и цвета бейджа, `isStale`) и ревизиями кадра и бейджей. Кадры анимации не идут через `StopMapState`, иначе на каждом кадре перестраиваются список остановок и панель ETA.
- [ ] Проверить нагрузку на CPU в Telegram WebView. Кадры идут не чаще 20 в секунду и меняют только GeoJSON-источник; с боевым BFF опрос двух маршрутов Батуми идёт раз в ~8 с без дублей. Если в WebView будет тяжело — синхронизировать публикацию с `requestAnimationFrame` на стороне адаптера, не меняя политику частоты в common.
- [x] Слой MapLibre: GeoJSON-источник и `symbol`-слой. Бейджи рисуются на canvas и регистрируются через `addImage` по ревизии бейджей, а не по кадру. Поворот по азимуту, только если он известен. Устаревшие позиции — пониженная непрозрачность и отдельный нецветовой признак, как в нативных адаптерах.
- [x] Нажатие на автобус передаёт `VehicleTapped` с ревизией кадра. В common это пока осознанный no-op, отдельного продуктового сценария не добавлять.
- [x] Статус слоя (`Loading`, `Stale`, `Retryable`, `Unavailable`, `Mixed`) под легендой маршрутов на трёх языках.
- [x] Невидимая сводка по `vehicleRoutes` (число автобусов и статус по каждому маршруту) в `aria-live=polite`, как в мобильных клиентах. Видимый статус больше не дублирует её объявлением.
- [x] Опрос останавливается, когда открыт каталог маршрутов (smoke) или карта скрыта (`jsTest`).
- [x] Smoke: `vehiclePositions` в фикстуре, бейдж на canvas (по цвету фар), отсутствие статуса при живых данных, пауза опроса за каталогом маршрутов.
- [x] Smoke для устаревших позиций: страница BFF со `stale: true` показывает статус «показаны более старые позиции» и снимает его со свежими данными.
- [x] Smoke для движения автобуса между опросами: следующий опрос сдвигает автобус, и по фарам на canvas видно промежуточные позиции, а не прыжок.
- [x] Опрос маршрута без автобусов больше не возвращает статус «загрузка» на время каждого запроса (`VehicleRealtimeReducer.markLoading`, общее для всех клиентов).
- [x] Поворот карты жестом и с клавиатуры отключён: правило переворота подписи на бейдже рассчитано на карту, смотрящую на север.
- [x] Бейджи перерисовываются при смене `devicePixelRatio` (масштаб страницы, другой монитор).
- [x] Пульсирующий ореол под автобусами цвета маршрута, с геометрией и ритмом нативных адаптеров (15 кадров/с, цикл 1,6 с, до 32 автобусов). При `prefers-reduced-motion`, скрытой странице и открытом каталоге маршрутов остаётся статичное кольцо. Smoke проверяет пульсацию и заморозку по пикселям canvas.

- [x] Тест моста в `jsTest`: кадры идут только в поток автобусов, опрос встаёт на паузу у скрытой карты, подписка освобождается вместе с `MapBridge`.
- [x] Проверено в локальном Chrome с боевым BFF: автобусы маршрута 1 в Батуми отрисованы бейджами цвета маршрута.

## Срез 3. Геолокация — ветка `feature/telegram-geolocation`

Общий контракт: `MyLocationClicked` и `RefreshLocation` → побочный эффект `HandleLocation(LocationPlatformCommand)` → адаптер отвечает `LocationEventReceived(LocationPlatformEvent)`. `LocationState` содержит разрешение, последнюю позицию и ошибку.

- [x] Адаптер `webApp/src/location.ts`. В Telegram 8.0+ — `Telegram.WebApp.LocationManager` (`init`, `getLocation`, `openSettings`; отказ → «нужны настройки»), иначе `navigator.geolocation` с Permissions API (отказ → «отклонено», настроек браузера мы не открываем). Неподдерживаемое открытие настроек отвечает явным `Error(canRetry)`, а не молчанием. Таймаут запроса 10 с, как в нативных адаптерах.
- [x] Точность: общая сессия связывает её с разрешением, а браузер сообщает только погрешность замера. Адаптер переключает разрешение на «примерное», если погрешность больше 250 м, иначе десктопные замеры по Wi‑Fi отклонялись бы как неточные.
- [x] Мост: `LocationStatus` и `UserLocation` (с кругом точности из common) в состоянии карты; `subscribeLocationCommands`, `myLocation`, `refreshLocation` и события `location*`. Все побочные эффекты VM идут через один сборщик — Orbit отдаёт каждый эффект только одному.
- [x] UI: кнопка «Моя геопозиция» с подписями и доступностью как в мобильных клиентах, точка (только при точной геопозиции) и круг точности в цветах нативных адаптеров, перевод камеры через `MapCameraCommand`. Текстовый статус разрешения появляется только после нажатия; ошибки запроса — сразу.
- [x] Жизненный цикл как на мобильных: разрешение перечитывается при открытии карты и возврате на страницу, запрос отменяется при скрытии карты, при выданном доступе позиция обновляется раз в 5 с.
- [x] Политика: без выданного доступа геолокация запрашивается только по нажатию; если доступ уже выдан, карта, как и в мобильных клиентах, сама определяет позицию при открытии. Отказ не блокирует карту. Позиция уходит только в существующий запрос ближайших остановок к BFF.
- [x] `jsTest`: команды до подписки не теряются, неизвестные состояния хоста игнорируются, выдача доступа запускает запрос, принятая позиция доходит до карты и центрирует её, ошибка и смена точности обрабатываются, после `dispose` команды не уходят.
- [x] Smoke: заглушка `LocationManager` — «нужно разрешение» → отказ Telegram → открытие настроек → возврат с доступом → точка на canvas.
- [x] Smoke для `navigator.geolocation` без Telegram: выданное заранее разрешение и `Emulation.setGeolocationOverride` → позиция определяется при открытии, точка на canvas.
- [ ] Проверка на реальных устройствах в Telegram (входит в срез 4).

## Построение маршрута A→B (MVP) — ветка `feature/journey-planner-web-mvp`

Решения — [ADR 0022](../adr/0022-batumi-in-house-journey-planner.md) (планировщик в BFF) и [ADR 0023](../adr/0023-journey-endpoints-and-coordinate-boundary.md) (точки A/B и граница координат). Этот срез — клиентская половина и только веб; Compose-UI для Android и iOS — отдельная работа, общий код для них компилируется.

- [x] Домен: `JourneyEndpoint` (`CurrentLocation`, `MapPoint`), `JourneyRequest`, `JourneyEndpointPolicy` — не больше одной стороны «Моё местоположение», A и B ближе 150 м → «вы уже на месте» без запроса, округление обеих точек до 4 знаков. `JourneyPlanQuery` не содержит признака, какая точка — геопозиция.
- [x] Данные: `POST /v1/cities/{cityId}/journeys/plan` в `TransitBffClient` без повторов, `BffJourneyPlanRepository` без кэша и без записи в офлайн-каталог. Новые поля `Journey`/`JourneySegment` необязательны; неизвестные `waitBasis`/`timingQuality` превращаются в «неизвестно» (ожидание тогда не считается живым), один битый вариант отбрасывается, а не роняет ответ.
- [x] Presentation по ADR 0018: срез `journeyPlanner` в `ViewState`, чистый `JourneyPlannerReducer`, владелец запросов `JourneyPlannerWorkflow` (поколение, latest-wins, проверка города, поколения и возможности `tripPlanning` внутри intent), `JourneyPlanUiMapper`. `MapViewModel` снова не длиннее 500 строк.
- [x] «Моё местоположение» берётся из существующей `LocationSession`: снимок не старше 120 с и точнее 250 м, проверка — прямо перед каждым запросом. Разрешение спрашивается только явной кнопкой «Моё местоположение» через существующий поток команд, длинное нажатие геопозицию не запрашивает. Отказ или примерная геопозиция оставляют выбор точки на карте.
- [x] Пока видны результаты, план пересчитывается раз в 60 с и при сдвиге геопозиции больше чем на 50 м; остановка при скрытии карты и закрытии панели, смена города всё очищает. Точки и ответы живут только в памяти Map: не попадают в сохранённое состояние, маршруты навигации, логи и аналитику.
- [x] Если в ответе есть маршрут, которого нет в каталоге, каталог города подгружается, чтобы бейджи и линии были в цветах BFF.

## Паритет UI с мобильными клиентами

Аудит веб-клиента против Android и iOS. Весь UI экрана карты на мобильных — общий Compose (`shared/src/mobileMain/.../map`), различаются только адаптеры карты (`PlatformMap.android.kt`, `MapLibreMapViewBridge.swift`).

### Карта

- [x] Остановки рисуются из `MapRenderState.stops`, а не из списка ближайших: мост отдаёт `stopLayer` (`MapStopLayer`: пины, кластеры, `stopSourceRevision`). Пин рисуется на canvas по геометрии `StopPinArtwork` из common (корпус, карточка с бейджами маршрутов, «+N» при трёх и более маршрутах) и регистрируется через `addImage` по `imageId`. Размер — `pinScale` (1,3; ×0,75 вне выбранных маршрутов; ×1,1 у выбранной), якорь снизу, как в нативных адаптерах.
- [x] Остановки выбранных маршрутов на малом зуме и группы остановок (`representsGroup`) приходят из common. Нажатие на пин идёт как `MapPlatformEvent.StopTapped` с ревизией (`MapBridge.tapStop`): устаревшая ревизия игнорируется, нажатие на группу приближает карту до 16, а не открывает ETA.
- [x] Выбранная остановка — отдельный источник и слой поверх автобусов, как `gt-selected-stop-*` на мобильных. Порядок слоёв: линии → круг точности → пины → кластеры → ореол → автобусы → выбранная остановка → точка пользователя.
- [x] Кластеры: круг `#264653` радиусом 12 с белой обводкой 2, как на мобильных, плюс счётчик внутри (на мобильных его нет). Нажатие на кластер, как и на мобильных, ничего не делает.
  - [ ] Common сейчас всегда отдаёт пустой `stopClusters` (`MapRenderProjector`), а события нажатия на кластер в `MapPlatformEvent` нет. Кластеризация и её нажатие — отдельное решение для всех клиентов сразу.
- [x] `jsTest` (`MapBridgeStopsTest`): цвета и бейджи пина для одного и двух выбранных маршрутов, масштаб вне маршрутов и у выбранной, нажатие с устаревшей ревизией игнорируется, с текущей — открывает ETA, неизменные остановки не перепроецируются.

- [x] Проверено с боевым BFF (Батуми, без маршрутов и с 10A, зум 13 и 15): пины как в мобильных, на зуме 13 без маршрута остановок нет, с 10A — только остановки маршрута; нажатие на пин открывает ETA.
- [x] Анимированные команды камеры (`MapCameraCommand.animated`, например приближение к группе) идут через `easeTo`; при `prefers-reduced-motion` — без анимации.
- [x] Viewport сообщается в ViewModel после любого перемещения камеры, в том числе программного, как `notifyViewportSettled` на мобильных. Иначе после приближения к группе ViewModel не видел нового зума.
- [ ] `viewportInsets.bottomOcclusionFraction` (0,42 у шторки ETA) не экспортируется. Пока панель на вебе не перекрывает карту, это не нужно. Если панель станет шторкой поверх карты — переводить долю в `padding` камеры.
- [ ] При откате на локальный стиль мобильные показывают плашку `map_preview_note` (`MapBaseLayerState.LocalPreview`). Веб переходит на него молча, `baseLayerState` не экспортирован.

- [x] Подпись источника для приблизительного времени: мост отдаёт `Approximate`, а веб ждал `ClientEstimate` и ничего не показывал.

## Известные ограничения и решения на потом

- Задача iOS в CI временно отключена (`if: false` в `.github/workflows/quality.yml`): она шла намного дольше остальных и тормозила слияние. Изменения в `shared/src/commonMain` сейчас не проверяются на iOS — перед релизом iOS гонять `:shared:iosSimulatorArm64Test` и сборку `iosApp` локально.
  - [ ] Включить iOS CI обратно после завершения основного функционала: удалить `if: false` у задачи `ios` и вернуть `ios` в `needs` задачи `publish-web`.
- Список остановок, легенды и панель ETA полностью перестраиваются на каждое состояние карты. Пока данных мало, это допустимо. Если на срезе 2 или на реальных устройствах появятся задержки, переиспользовать DOM-узлы по id.
- Атрибуция из конфигурации BFF вставляется MapLibre как HTML. Источник — наш BFF, но конфиг должен содержать только безопасную разметку.
- Chromium на Android, по всей видимости, не отражает системный масштаб шрифта в размере `medium` без `<meta name="text-scale" content="scale">`, а этот тег масштабирует и весь интерфейс на `rem`. Включать его — отдельным решением вместе с проверкой вёрстки и в Telegram на Android.
- Dev-сервер по умолчанию проксирует `/v1/` на продовый BFF; для локального BFF задаётся `TRANSIT_BFF_ORIGIN`. Клиент можно разместить в подпапке, но `/v1/` должен оставаться в корне origin.
